## Findings that change the plan

1. **Installed recipe PWAs will outlive any redirect unless two worker URLs stay 200.** `src/components/recipes/recipe-pwa-client.mjs` registers `/recipe-service-worker.js` with scope `/`; `scripts/recipes/pwa-build.mjs` also writes a legacy worker at `/post/15-minute-dump-and-go-instant-pot-recipes/service-worker.js`. Both are live (200) today. Browsers reject a redirected worker script on update, and the cached worker answers navigations for the recipe route and listed assets from its cache, so those clients never reach the 301. Disposition for both: serve a 200 kill-switch worker on blogthedata.com (unregister, delete caches starting `recipe-pwa-` and `recipe-pages-pwa-`, navigate open clients to `https://www.jsolly.com/recipes/`) and exclude both paths from the redirect set. Installed home-screen apps are origin-bound and cannot migrate; users re-install from jsolly.com. The manifest `id`/`start_url` is `/post/15-minute-dump-and-go-instant-pot-recipes/`. Exposure is small (recipes app is days old) but real. The recipe route's `Cache-Control: no-cache` header rule in the old `vercel.json` must be carried to the redirect-only project for the worker path.
2. **Status code: 308 is what Vercel emits by default.** `permanent: true` yields 308 (live site returns 308 for bare paths and for the apex). John asked for 301. Rules need an explicit status code (Vercel's bulk-redirects API excerpt confirms `statusCode` 301/302/307/308; the `vercel.json` `statusCode` field is from the schema and was not shown in the doc excerpt retrieved this session, so confirm on first deploy). Trailing-slash 308s (`trailingSlash: true`) are separate and cannot be 301 unless that setting changes on the redirect-only project; verification should therefore assert final destination and a hop limit rather than "exactly one 301".
3. **Closed-loops alias ends in a 404.** `/post/how-to-leverage-closed-loops/` -> `/post/stop-asking-questions-to-save-time/`, which is missing on the live site and was missing on the old Heroku site (docs/astro-migration.md records this as deliberate). Entry keeps the recorded destination (so the redirect-coverage test must whitelist a 404 final status) and lists `/blog/how-to-ask-less-questions/` as an alternative for John. Do not retarget silently.
4. **Five historically indexed posts are gone.** Seen in Wayback, absent from the 106-record final export (deleted before Oct 2): `blogthedata-open-source-blog-portfolio`, `family-constitution-outlines-principles-values`, `geoasteroids`, `part-1-adding-SEO`, `web-mapping-gallery`. Suggested targets are in the JSON with confidence and an alternative; all are `decision_needed`. Only `geoasteroids` is a clear topical match.
5. **Case sensitivity.** Django lookups were exact (`filter(slug=...)`), so lowercase variants of mixed-case post slugs (`/post/achieve-consistent-builds-...`) never worked; they are not in the map. Category slugs were different history: `/category/geodev/` returned 200 until 2023-05 and `/category/Geodev/` from 2023-12. Both rows exist. Whether Vercel `redirects` source matching is case-sensitive is UNVERIFIED; if it is not, the `geodev` and `Geodev` rows collide (same destination, so harmless) but the coverage test must check both spellings and the post-slug rows must not produce loops with a case-insensitive filesystem lookup on the destination. The merged site must keep mixed-case post slugs exactly or add rows.
6. **Media hosts are outside any Vercel redirect.** Posts reference `https://d1d7p8ufhgz4ld.cloudfront.net/media/...` 213 times; Django's `STATIC_HOST`/`AWS_S3_CUSTOM_DOMAIN` (`<bucket>.s3.amazonaws.com`) also served media. Archiving awesome-blog must not retire the S3/CloudFront stack ("retained until separately authorized retirement" per docs). jsolly-website's CSP is `img-src 'self' data:` (vercel.json) so CloudFront images will be blocked on jsolly.com until images are same-origin or the CSP is widened: that is a build/CSP issue for the plan, not a redirect issue.
7. **Old-host media paths.** Wayback saw `/media/post_metaimgs/*` (124 paths, all still 200 on CloudFront), `/media/django_ckeditor_5/*` (44), `/media/uploads/*` (13), `/media/profile_pics/*` (1) on blogthedata.com itself. Only 1 path (`/media/default.webp`) resolves on the live host now (as a built asset), the rest 404. Pattern redirect for `post_metaimgs` is verified 124/124. For the 57 ckeditor/upload files, 48 share a filename with `post_imgs/*` on CloudFront and 37 of those have byte-identical `Content-Length` to the Wayback original; only those 37 are redirected, the rest are drop-404 (filename alone is unsafe for names like `image.png`). Same-size is strong, not cryptographic, evidence. Low traffic; this whole block is optional. The final media host is plan decision D-media.
8. **Redirect-only host needs a real 404 and a permissive robots.txt.** `robots.txt` today has `Disallow: /search/` and a Sitemap line for the old host; the redirect-only project should serve an allow-all robots.txt with no Disallow so crawlers can follow the 301s (a redirect of robots.txt itself is not recommended). Unmapped paths (bot probes, `/static/*`, `/cdn-cgi/*`, account routes) must 404, not be swept into a catch-all to `/blog`.
9. **Query-string behavior is unverified.** `/?page=N`, `/category/*/?page=N` and `/search/?searched=` return 200 on the live host. Whether Vercel forwards or drops the query on redirect, and whether `has: query` is needed to match, was not verified; the coverage test should exercise one query URL per family.
10. **Recipe anchors.** The old article carried 12 fragment anchors (recipe ids). A fragment survives the 301 only if `/recipes/` uses the same ids on the destination page; `/recipes/` also needs to exist as an index (it is 404 on the old host today because only `/recipes/meals/`, `/recipes/smoothies/` and per-recipe pages exist).
11. **`/data/recipe-library.json|md` may have external consumers** (assistant/custom-assistant usage). No URL consumer is documented in the repo (UNVERIFIED), so treat these two as must-redirect.
12. **Self-links inside posts.** Posts contain ~76 absolute `https://(www.)blogthedata.com/...` link occurrences (e.g. `/post/how-to-get-a-perfect-mozilla-observatory-score/` x4, `/productivity?page2`, `/admin`, `/doesnotexist`). They are content for the internal-link rewrite step; a few are intentional illustrative dead links (Django tutorial posts) and should not be "fixed". `jsolly-website` itself links blogthedata via `src/images/social/blogthedataLogo.svg` / `socialLinks.ts`.
13. **Pre-slug URLs.** `/post/<int:pk>/` existed 2020-08-08 to 2022-02-02 (commit 06ef0e1d, no redirect shim). Zero Wayback captures and zero search evidence, dead for 4.7 years; recommended skip. If John wants them anyway, 106 rows can be generated from each post's `legacyId` (assumed equal to the old pk, UNVERIFIED).
14. **Search Console.** Domain move tooling (Change of Address) and sitemap handling for moving into a path on an existing property (`www.jsolly.com/blog/`) were not verified; UNVERIFIED, belongs in the cutover phase.
