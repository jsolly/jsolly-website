Vercel behaviour (observed live with curl):
- No-slash variants 308 to slash form (`/rss` -> `/rss/`, `/post/X` -> `/post/X/`, `/recipes/meals` -> `/recipes/meals/`). `/rss/` 200 `application/rss+xml`, `/atom/` 200 `application/atom+xml` (headers rule in vercel.json). In dist these are extensionless files `rss` and `atom`.

- Query strings are carried through Vercel redirects (observed `?x=1&page=2` preserved, including the apex-host redirect `blogthedata.com` -> `www`). Fragments are never sent to server; browsers re-apply the original fragment across a redirect with no fragment in Location (standard HTTP behaviour; not browser-tested here, UNVERIFIED).

## 7. Service workers: critical cutover hazard

`recipe-pwa-client.mjs:10` registers `/recipe-service-worker.js` with `{scope:'/'}` (root of blogthedata.com) on every page that includes `RecipePwa` (the library post and all 23 `/recipes/*` pages). `pwa-build.mjs` generates two workers: `/recipe-service-worker.js` (cache `recipe-pages-pwa-<hash>`) and the legacy `/post/15-minute-dump-and-go-instant-pot-recipes/service-worker.js` (scope = that path, cache `recipe-pwa-<hash>`). The worker answers GET fetches for any URL in its `ASSETS` list (the library page, every `/recipes/<slug>/` page, `/_astro/*`, `/media/recipes/*`, `/data/*`, `/favicon.ico`) from cache, with no network call, for navigations to slash-terminated URLs. `activate` claims clients; updates install in `waiting` and only activate after all tabs close.
Consequences once blogthedata.com becomes redirect-only (spec-based reasoning, not tested here: UNVERIFIED):
1. Any browser that visited a recipe page keeps rendering the cached `/post/15-minute-.../` and `/recipes/<slug>/` pages instead of following the 301 to jsolly.com/recipes.
2. If `/recipe-service-worker.js` or the legacy `/post/15-minute-.../service-worker.js` starts returning a redirect, the browser's service-worker update check fails (SW script fetches must not redirect; W3C ServiceWorker "Update" algorithm), so the stale worker is never replaced.
Therefore the redirect-only deployment must keep these two paths served as 200 with a kill-switch worker (clear `recipe-pages-pwa-*` and `recipe-pwa-*` caches, `registration.unregister()`, then `clients.matchAll().navigate(<jsolly url>)`), with `Cache-Control: no-cache`, and exclude them from any catch-all redirect. This works only while the blogthedata.com project/domain stays alive (supports "keep redirects alive after repo archive").
3. Installed PWAs (manifest `start_url` is the library post): they will open standalone to blogthedata.com then bounce cross-origin to jsolly.com; the new jsolly.com recipes page needs its own manifest/scope (`/recipes/`) and cannot take over the old install.
